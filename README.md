## О проекте

По заданию нужно было сделать интерфейс, через который можно написать человеку в MAX и получить от него ответ. Всё через GREEN-API: отправка методом `SendMessage`, получение через HTTP API (`ReceiveNotification` и `DeleteNotification`). За образец внешнего вида взят web.max.ru.

Зарегистрироваться в MAX у меня не получилось, поэтому основной сценарий я проверял на Telegram: задание это допускает. Приложение при этом работает с обоими мессенджерами. При входе оно смотрит тип инстанса и подстраивается под него. API у MAX и Telegram почти одинаковый, отличия собраны в [src/lib/messenger.ts](src/lib/messenger.ts).

Сценарий из задания работает так. Вводите `idInstance` и `apiTokenInstance`, нажимаете «+», вводите номер телефона. Приложение проверяет номер через `CheckAccount` и открывает чат. Пишете сообщение, собеседник отвечает в мессенджере, ответ появляется в чате через пару секунд.

Потом я довёл приложение до состояния, в котором им правда можно пользоваться:

- подтягиваются существующие чаты с аватарами и последними сообщениями;
- при открытии чата загружается история;
- видны статусы доставки и прочтения;
- свои сообщения можно редактировать и удалять;
- собеседник видит, что вы печатаете.

В профиле можно поменять фото и включить нужные уведомления инстанса. Если инстанс настроен так, что сообщения не дойдут, приложение скажет об этом и предложит исправить.


## Запуск

Нужен Node.js 20 или новее.

```bash
git clone <repo-url>
cd green-api-chat
npm install
npm run dev
```

Приложение откроется на http://localhost:5173.

Другие команды: `npm test` запускает тесты, `npm run lint` проверяет код линтером, `npm run build` собирает production-версию в `dist/`.

## Как устроено

Бэкенда нет. GREEN-API разрешает запросы из браузера, поэтому приложение ходит в API напрямую.

Стек: React 19, TypeScript, Vite, Tailwind CSS. Отдельной библиотеки для состояния нет. Всё состояние чатов лежит в одном reducer ([src/store/chatReducer.ts](src/store/chatReducer.ts)): это чистая функция, её удобно тестировать. `ChatProvider` связывает reducer с API, а фоновые задачи вынесены в хуки: опрос уведомлений, синхронизация чатов, работа с открытым чатом и так далее.

```
src/
├── api/          клиент GREEN-API и эмулятор для демо
├── store/        reducer, провайдер, контексты
├── hooks/        опрос уведомлений, синхронизация чатов и вкладок, действия с сообщениями
├── lib/          разбор уведомлений, хранилище, форматирование, телефоны
└── components/   интерфейс
```

## Что было непросто

**Номер телефона и id чата — разные вещи.** Сообщение можно отправить по номеру, но ответ приходит с внутренним id пользователя. Если завести чат по номеру, ответ окажется в другом чате. Поэтому перед созданием чата номер проверяется через `CheckAccount`, который возвращает настоящий id.

**Очередь уведомлений может встать.** Если не удалить уведомление после обработки, GREEN-API будет отдавать его снова и снова. Поэтому удаление вызывается всегда: и для ненужных уведомлений, и если обработка упала.

**Несколько вкладок.** Очередь у инстанса одна. Если открыть приложение в двух вкладках, они начнут делить сообщения между собой. Сейчас очередь читает только одна вкладка, остальные получают события от неё. Если эту вкладку закрыть, опрос подхватит другая.

**Лимиты API.** У каждого метода GREEN-API своё ограничение по частоте: настройки можно запрашивать раз в секунду, аватары — десять раз. Клиент сам раскладывает запросы по времени. Фоновые запросы не занимают все соединения браузера, иначе опрос уведомлений стоял бы в очереди.

**Статусы приходят не по порядку.** «Доставлено» может прийти после «прочитано», а статус иногда приходит раньше, чем ответ на саму отправку. Reducer это учитывает: статус не откатывается назад и не теряется.

**Удалённые чаты.** Уведомления об удалении чата в API нет. Поэтому список раз в минуту сверяется с `GetChats`: если чат пропал оттуда, он пропадает и в приложении.

## Тесты

211 тестов на Vitest. В основном они проверяют логику: reducer, разбор уведомлений, клиент API (ошибки, повторы, лимиты), опрос очереди, хранилище и форматирование дат. CI на GitHub Actions на каждый push запускает линтер, тесты и сборку.

## Ограничения

- Токен хранится в браузере. Для учебного проекта это нормально, в настоящем продукте запросы лучше проксировать через свой сервер.
- Если войти с одним инстансом из двух разных браузеров, уведомления разойдутся между ними. Вкладки одного браузера договариваются между собой, разные браузеры — нет.
- История чата грузится последними 50 сообщениями: API не умеет отдавать её постранично.
- Медиа не показываются, вместо них подпись вроде «Фото» или «Стикер». По заданию нужен только текст.
- Через API можно поменять только фото профиля, имя и описание — нет.
